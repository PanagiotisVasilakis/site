# Offline architecture (summary)

This document explains the offline support in this repo, how precaching/versioning works, and quick commands to test and maintain it.

Key components

- Service worker: `public/sw.js` — custom SW implementing precache + runtime caching and an analytics queue.

- Precache manifests: `public/precache.json` (full) and `public/critical-precache.json` (smaller, used at install).

- Version metadata: `public/version.json` generated by `scripts/generate-version.ts`.

- Generator script: `scripts/generate-precache.ts` produces both precache files. Use `PRECACHE_ITEMS_PER_CATEGORY` to control critical size.

- Client PWA manager: `src/components/PwaManager.tsx` registers SW and presents update banners.

Runtime behavior

- On `install`, SW fetches `version.json` to compute a cache name including version and precacheHash. It then attempts to precache assets listed in `critical-precache.json` (fallback to `precache.json`).

- On `activate`, SW cleans old caches and broadcasts runtime version to clients.

- Fetch strategies:

  - JSON endpoints: stale-while-revalidate (serve cached JSON immediately if present, update cache in background).

  - HTML navigation: offline-first (return cached HTML if present; revalidate in background; fallback to `/offline`).

  - Images/static: stale-while-revalidate with validation.

  - Analytics POSTs: queued in IndexedDB when offline and flushed via Background Sync when available.

Developer commands

- Generate precache and version (run before build):

  - `npm run build` (runs `generate-precache` and `generate-version` before `next build`)

  - Or run generator manually: `npx tsx scripts/generate-precache.ts`

- Start dev server: `npm run dev`

- Simple static smoke-test (after serving `public/`):

  - `npx http-server public -p 3000`

  - `npm run check:offline-assets` (script checks `/sw.js`, `/precache.json`, `/critical-precache.json`, `/version.json`, `/manifest.webmanifest`)

Recommendations

- Keep `critical-precache.json` small (default 3 items per category). Adjust `PRECACHE_ITEMS_PER_CATEGORY` in CI if needed.

- Verify your analytics endpoint accepts the merged-array payload from the SW flush; if it doesn't, update the SW to send items individually.

- Monitor cache sizes and add eviction policies if your site grows.

- Consider adding observability (metrics) for cache hits, prewarm success rates, and queue sizes.

Troubleshooting

- If dev server binding causes the smoke-test to fail locally, run the static server against `public/` as shown above and re-run `npm run check:offline-assets`.

Analytics endpoint expectations

- Endpoint: `POST /api/analytics`

- Payload: the SW will try to deliver queued analytics as individual POSTs. Each POST body is a JSON string representing a single analytics event or a small batch as emitted by the client. Example shape expected by server:

```json
{
  "path": "/en/restaurants/sea-breeze",
  "ts": 1695900000000,
  "locale": "en",
  "event": { "name": "click", "props": { "button": "save" } }
}
```

- Behavior in the SW: when offline, the client attempts `navigator.sendBeacon` or a regular fetch; if both fail the client posts a message to the SW which stores the event (stringified) in IndexedDB. On `sync` or `flushQueue()` the SW attempts to POST each queued item individually. If a POST fails, that item is re-enqueued for the next attempt.

- Server compatibility: make sure `/api/analytics` accepts a single JSON event per POST. If your server accepts arrays, the SW previously attempted to submit a merged array; the current behavior posts individually for wider compatibility.

- Testing the queue locally: while offline, trigger analytics events (e.g., navigate or click in the app). Reconnect; if Background Sync isn't available, open a client and send the `REPLAY_ANALYTICS` message to the SW from the console:

```js
navigator.serviceWorker.controller.postMessage({ type: 'REPLAY_ANALYTICS' });
```

The SW will attempt to flush the queue and POST events to `/api/analytics`.
